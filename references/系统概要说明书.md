# 系统概要说明书（md 格式）生成规范

本文件指导如何从原型解析数据生成系统概要说明书。当用户要求生成“系统概要说明书”“系统概要设计”或“概要设计文档”时读取本文件。

## 输出文件

- 文件名：`系统概要说明书.md`
- 位置：原型目录下 `output/` 或用户指定位置
- 格式：Markdown（`.md`）
- 生成脚本：`scripts/generate_spec_docs.py --doc-type system-overview`

## 文档定位

系统概要说明书回答“这个系统做什么、由哪些模块组成、边界在哪里、有哪些非功能约束”，不展开到单个按钮和字段级实现。详细交互放到《详细说明书》，表结构放到《数据库设计说明书》。


## 各章节生成规则

### 1. 引言

- **编写目的**：说明本文档用于建设目标、总体架构、功能范围与非功能要求，作为设计评审、开发实现、测试验收与上线运维依据。
- **适用范围**：列出纳入本次说明书的页面；超过 12 页时列前 12 页并注明总页数。
- **术语与缩略语**：至少包含“原型 / 页面 / 字段 / P0-P2 / 待确认”。
- **参考资料**：原型解析工具、原型根目录、页面数量。

### 2. 系统概述

- **项目背景**：只能基于原型文本归纳；原型未提供业务背景、现状问题、建设动因时，明确写“需业务方补充”，不得编造行业背景。
- **建设目标**：不要逐页罗列。建议输出三项：
  1. 覆盖模块数与功能项数；
  2. 按功能数排序的重点模块（最多 6 个）；
  3. 页面类型分布（配置页 / 管理后台 / 表单页 / 列表页 / 流程页等）。
- **用户角色**：按 `page_category` 推断，至少给出角色名与职责；无依据时只保留“系统用户”。
- **运行环境**：技术栈、部署方式、服务器/操作系统/中间件/网络要求无法从原型判断时统一标“待确认（原型未声明）”。

### 3. 总体设计

- **设计原则**：职责单一、可扩展、安全合规、可运维；均为原则性描述，不绑定具体技术。
- **系统架构**：说明“原型仅体现前端页面与交互”，架构风格、技术栈、部署方式待确认；可给出接入层 / 应用层 / 服务层 / 数据层 / 基础设施的建议分层表，但必须标注“建议，待确认”。
- **模块划分**：按页面或页面组划分模块，给出模块名、功能项数、主要功能、优先级。
- **核心业务流程**：优先提取页面跳转、打开新页面、提交、发布等业务动作；过滤“设置尺寸、显示/隐藏、旋转、选中状态、动态面板”等纯 UI 状态描述。无业务动作时写“原型未体现跨页面业务流转，待补充”。
- **部署与集成**：原型未提供部署拓扑、第三方系统、消息/定时任务时标“待确认”，不得虚构中间件。

### 4. 功能概要

功能清单表建议列：

| 列 | 说明 |
|----|------|
| 功能编号 | `F-001` 全局递增 |
| 模块 | 页面名或页面组名 |
| 功能名称 | 动作 + 对象，如“查看实例列表”“新增节点” |
| 所属页面 | 原型页面名 |
| 优先级 | P0 核心 / P1 重要 / P2 一般 |
| 功能描述 | 一句话说明业务价值与主要操作 |

便签、业务规则与待确认项写入功能描述或附录，不单独增加“备注”列。功能项至少覆盖：页面主功能、筛选查询、表单填写与提交。避免把纯展示文本、装饰性按钮当成独立功能。

### 5. 接口概要

- 原型通常没有接口定义，本节输出“建议接口”，必须标注“建议，待确认”。
- 按实体/页面推断读取、保存、查询、发布等接口；给出接口名称、类型、提供方、调用方、说明。
- 路径建议使用 `/api/<资源>`、`/api/<资源>/{id}`，不要虚构网关、鉴权、消息队列等实现细节。

### 6. 数据与实体概要

- 给出实体清单（实体名、建议表名、来源页面、字段数、说明）。
- 给出实体关系概要（1:1 / 1:N / N:M），关系仅基于页面命名与字段推断时标注“基于页面命名推断”。
- 不展开完整字段定义，字段级内容放到《数据库设计说明书》。
- 没有可用字段时写“原型未识别到可用字段，实体与表设计待补充”。

### 7. 非功能需求

至少覆盖：

| 类别 | 默认基线（待确认） |
|------|------------------|
| 性能 | 普通查询 P95 ≤ 2s，写操作 P95 ≤ 3s |
| 并发 | 按日活与峰值估算，原型未提供 |
| 可用性 | 核心功能可用性 ≥ 99.5% |
| 安全 | 身份认证、最小权限、敏感字段加密、操作审计 |
| 兼容性 | Chrome / Edge 最近两个大版本；移动端按需 |
| 可维护性 | 统一日志、监控、告警、配置管理 |
| 合规 | 按行业与数据类型补充，原型未体现 |

默认基线只是编写起点，必须标注“待确认”，不能写成已确认指标。

### 8. 约束与假设

- **约束条件**：原型仅提供页面、控件与交互，不含后端、数据库、部署信息；字段、接口、表结构需在详细设计与数据库设计阶段确认。
- **前提假设**：页面名称近似代表业务模块；原型文本与控件即当前需求来源；原型未展示的规则不视为已确认需求。
- 如补充实施顺序或风险，可放入本节，但必须标注“建议/粗估”。

### 附录

- 待确认事项：合并字段歧义、缺失业务规则、未确认技术栈。
- 变更历史：版本、日期、变更内容、变更人。
- 数据来源说明：解析工具、原型目录、覆盖页面数、推断实体数、未纳入页面、便签纳入情况。

## 便签/备注说明的纳入

- 业务规则、范围说明、约束条件优先放入“功能描述”“功能边界”或附录待确认项。
- 无法判断归属的备注放入“待确认事项”，不要丢弃。
- 在“数据来源说明”标注：便签/矩形内备注说明已纳入功能描述、功能边界或待确认项。

## 生成脚本

```bash
# 1. 解析原型
python3 scripts/parse_axure.py <原型目录> --json > prototype.json

# 2. 生成系统概要说明书
python3 scripts/generate_spec_docs.py prototype.json output/系统概要说明书.md \
  --doc-type system-overview --version v1.0.0
```

可选参数：

- `--project-name <名称>`：覆盖解析结果中的项目名。
- `--version <版本>`：写入封面版本号。

脚本只负责结构化初稿；生成后仍需人工复核业务背景、角色、接口与非功能指标。

## 使用要点

1. **只写原型能支撑的内容**：无法判断的统一标“待确认”，不编造业务价值。
2. **概要不展开实现**：不写具体表字段、按钮级交互和代码方案。
3. **模块与功能要对齐**：功能清单中的每个功能必须能归属到一个模块和一个页面。
4. **接口是建议**：路径、方法、提供方均需后端确认。
5. **非功能是基线**：默认指标只用于评审起点，不能当成需求已确认。
