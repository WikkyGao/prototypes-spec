# 试运行报告规范

## 用途

用于记录系统在试运行环境中的准备、执行、问题与结论，作为上线决策、整改验收和运维交接的依据。适用于新系统上线前、重大版本升级后或迁移切换前的试运行。

不适用于：

- 日常测试报告（应使用测试用例与缺陷管理工具）
- 正式上线后的运行月报
- 仅做页面验收、没有真实执行记录的“纸面试运行”

## 输入与数据来源

| 输入 | 用途 |
|------|------|
| 原型解析 JSON | 页面、模块、功能项、接口、角色与字段 |
| 试运行计划 | 时间、环境、参与人、范围 |
| 测试/缺陷记录 | 执行结果、问题编号、严重级别 |
| 监控与日志 | 响应时间、成功率、可用性、错误量 |
| 业务反馈 | 功能完整性、操作便捷性、规则补充 |

原型只能提供“应验证什么”，不能提供“实际结果”。所有执行结果、指标和结论必须来自真实试运行记录；没有记录时统一写“待确认/待执行”，不得编造通过率。

## 文档结构

### 1. 引言

- 1.1 编写目的：说明报告用于上线决策与整改验收。
- 1.2 适用范围：列出页面范围、试运行环境和不在范围内的内容。
- 1.3 术语与缩略语：原型、页面、字段、P0/P1/P2、待确认。
- 1.4 参考资料：试运行计划、测试用例、缺陷清单、监控报表。

### 2. 试运行概述

- 2.1 系统简介：页面数、模块数、功能项数、试运行边界。
- 2.2 试运行目标：功能、流程、接口、权限、数据、性能、稳定性、可运维性。
- 2.3 试运行范围：模块表（模块/功能项数/主要功能）。
- 2.4 试运行环境：应用地址、版本、数据库、中间件、操作系统、网络。
- 2.5 试运行时间与人员：阶段、计划时间、参与角色、职责。

### 3. 试运行准备

- 3.1 环境与部署检查：应用、数据库、配置、网络、日志监控、备份回滚。
- 3.2 测试数据准备：基础字典、业务主数据、异常数据、脱敏要求。
- 3.3 人员与培训：业务用户、测试人员、运维人员。
- 3.4 准入检查清单：环境差异、版本归档、数据脱敏、时间窗口、问题模板。

### 4. 试运行执行

- 4.1 功能验证：功能编号、模块、功能、优先级、验证结果、问题编号。
- 4.2 业务流程验证：流程/页面、关键步骤、验证结果、问题编号。
- 4.3 接口验证：接口名称、类型、说明、验证结果、问题编号。
- 4.4 非功能验证：并发、数据保留、删除、安全、可用性等基线。

### 5. 试运行结果

- 5.1 功能结果汇总：功能总数、P0/P1/P2 数量、已验证数、通过率。
- 5.2 缺陷与问题清单：编号、模块、问题描述、严重级别、状态、责任人、计划修复时间。
- 5.3 运行指标：响应时间、接口成功率、可用性、错误日志量、操作完成率。
- 5.4 业务反馈：功能完整性、操作便捷性、业务规则补充。

### 6. 问题整改与上线建议

- 6.1 整改计划：问题编号、措施、责任人、完成时间、验证方式。
- 6.2 风险评估：核心功能、性能、数据迁移、权限配置等风险。
- 6.3 上线建议：明确“建议上线/有条件上线/不建议上线”，并列出限制条件。

### 7. 试运行结论

- 7.1 结论：是否满足上线条件、遗留问题、限制条件。
- 7.2 后续工作：缺陷修复、文档更新、上线审批、备份与回滚演练。

### 附录

- 待确认事项
- 变更历史
- 数据来源说明
- 可选：执行记录、监控截图、缺陷统计

## 表格列定义

### 功能验证表

| 列 | 说明 |
|----|------|
| 编号 | 功能编号，与功能清单一致 |
| 模块 | 所属页面/模块 |
| 功能 | 功能名称 |
| 优先级 | P0/P1/P2 |
| 验证结果 | 通过/不通过/阻塞/待执行 |
| 问题编号 | 关联缺陷编号，无则填“-” |

### 缺陷清单

| 列 | 说明 |
|----|------|
| 编号 | BUG-001 递增 |
| 模块 | 问题所属模块 |
| 问题描述 | 现象、复现步骤、预期与实际 |
| 严重级别 | 阻塞/严重/一般/建议 |
| 状态 | 待处理/修复中/待回归/已关闭 |
| 责任人 | 开发或模块负责人 |
| 计划修复时间 | 日期或版本 |

### 运行指标

| 指标 | 建议目标 | 数据来源 |
|------|----------|----------|
| 页面平均响应时间 | 待确认 | APM/网关日志 |
| 核心接口成功率 | 待确认 | 接口监控 |
| 系统可用性 | 待确认 | 监控平台 |
| 错误日志数量 | 待确认 | 日志平台 |
| 用户操作完成率 | 待确认 | 业务统计/观察记录 |

## 结论判定规则

- **建议上线**：P0/P1 功能全部通过，无阻塞级缺陷，性能与安全指标达标，回滚方案已验证。
- **有条件上线**：核心功能通过，存在可控的一般缺陷，已明确整改时间与规避措施。
- **不建议上线**：核心功能不通过、存在阻塞级缺陷、数据一致性或安全风险未解决。
- 结论必须引用具体执行记录；没有记录时只能写“待试运行完成后确认”。

## 便签/备注说明的纳入

- 业务规则、范围说明、约束条件优先放入“试运行目标”“试运行范围”或“风险评估”。
- 无法判断归属的备注放入“待确认事项”，不要丢弃。
- 在“数据来源说明”标注：便签/矩形内备注说明已纳入验证记录、问题清单或待确认项。

## 质量检查

- [ ] 是否明确试运行环境、时间、参与人和范围
- [ ] 功能验证是否覆盖 P0/P1 功能
- [ ] 接口、权限、数据、性能是否都有验证项
- [ ] 缺陷是否有严重级别、责任人和状态
- [ ] 结论是否基于真实记录，是否给出上线建议
- [ ] 所有原型未体现的内容是否标注“待确认”
