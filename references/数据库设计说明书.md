# 数据库设计说明书（md 格式）生成规范

本文件指导如何从原型解析数据生成数据库设计说明书。当用户要求生成“数据库设计说明书”“数据库设计文档”“表结构设计”时读取本文件。

## 输出文件

- 文件名：`数据库设计说明书.md`
- 位置：原型目录下 `output/` 或用户指定位置
- 格式：Markdown（`.md`）
- 生成脚本：`scripts/generate_spec_docs.py --doc-type database-design`

## 文档定位

数据库设计说明书回答“系统需要哪些表、每张表有哪些字段、字段类型与约束是什么、表之间怎么关联、索引怎么建”。它是开发建表和 DBA 评审的依据，但所有内容只要来自原型推断，就必须标注“建议，待确认”。

## 各章节生成规则

### 1. 引言

- **编写目的**：说明本文档用于数据库选型、逻辑模型、物理表结构与索引设计，作为开发与 DBA 建库建表依据。
- **适用范围**：列出纳入的页面；超过 12 页时列前 12 页并注明总页数。
- **术语与缩略语**：原型、页面、字段、P0-P2、待确认。
- **参考资料**：解析工具、原型根目录、页面数量。

### 2. 设计概述

- **设计原则**：满足第三范式、统一主键与审计字段、不使用物理外键、敏感字段加密、命名可读。
- **数据库选型**：默认 MySQL 8.0、`utf8mb4`、`utf8mb4_general_ci`、UTC+8；均标注“默认，待确认”。
- **命名规范**：

| 对象 | 规范 | 示例 |
|------|------|------|
| 表名 | `t_` + 小写下划线 | `t_instance` |
| 字段名 | 小写下划线 | `created_at` |
| 主键 | 统一 `id` | `id` |
| 外键 | `<实体>_id` | `instance_id` |
| 索引 | `idx_<表>_<字段>` | `idx_instance_status` |
| 唯一索引 | `uk_<表>_<字段>` | `uk_user_username` |

- **字段类型映射**：

| 原型控件/标签 | 建议类型 | 说明 |
|--------------|---------|------|
| 单行输入框 | `varchar(128)` | 长度按业务确认 |
| 多行文本 | `text` | 长文本 |
| 数字输入 | `int` / `decimal(18,2)` | 金额用 decimal |
| 日期选择 | `datetime` | 需要时区时用 timestamp |
| 下拉/单选 | `varchar(32)` / `tinyint` | 枚举值待确认 |
| 复选框 | `tinyint(1)` | 0/1 |
| 密码 | `varchar(255)` | 加密存储 |
| IP | `varchar(64)` | 兼容 IPv6 |
| URL | `varchar(512)` | 长链接 |

### 3. 逻辑数据模型

- **实体清单**：实体名、建议表名、来源页面、字段数、说明。
- **实体关系图**：使用 Mermaid `erDiagram`，只画能从页面命名/字段推断的关系；没有可靠关系时在图中用注释说明“关系待确认”。
- **关系说明**：关系类型（1:1 / 1:N / N:M）、关联字段、推断依据；基于命名推断时明确标注。

### 4. 物理表设计

每张表包含三部分：

#### 表信息

| 属性 | 值 |
|------|-----|
| 表名 | `t_xxx` |
| 中文名 | 中文实体名 |
| 说明 | 来源页面与页面类型 |
| 主键 | `id` |

#### 字段定义

| 序号 | 字段名 | 类型 | 长度 | 允许空 | 默认值 | 约束/索引 | 说明 |
|------|--------|------|------|--------|--------|-----------|------|

规则：

1. 每张表必须有 `id bigint` 主键。
2. 每张表必须有 `created_at`、`updated_at`，默认 `CURRENT_TIMESTAMP`，不允许为空。
3. 业务字段名使用小写下划线；中文标签能映射到通用英文时优先映射，不能映射时用 `field_<序号>`。
4. 字段类型无法判断时用 `varchar(128)`，并在说明中标注“类型待确认”。
5. `required` 为“待确认”时，“允许空”列必须写“待确认”，不能擅自转成“否”。
6. 默认值未知时写 `-`，不要写“待确认”。
7. 主键、唯一键、普通索引在“约束/索引”列标注 `PK`、`UK`、`IDX`；索引建议需在索引表中展开。
8. 没有业务字段的表不要生成；在附录“未纳入表设计”中说明。

#### 索引设计

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|

规则：

- 主键索引固定为 `PRIMARY`。
- 外键字段、高频筛选字段、状态字段可建议普通索引。
- 唯一业务编号建议唯一索引。
- 所有索引标注“建议，待确认”，不承诺最终执行计划。

### 5. 数据字典

- 将各表字段按字段名去重，输出全局字段字典：字段名、类型、说明、所属表。
- 同一字段出现在多张表时，“所属表”列用逗号分隔，不重复建行。
- 用于和《数据字典》交付物交叉核对；字段名、类型、说明以物理表为准。
- 没有实体时写“待补充”。

### 6. 索引与约束设计

- **6.1 索引策略**：高频查询字段建普通索引；唯一业务标识建唯一索引；组合索引遵循最左前缀；索引均为建议，需结合查询与数据量确认。
- **6.2 约束策略**：主键非空唯一；业务唯一键由唯一索引保证；关联完整性由应用层校验；原型未提供外键与级联策略时明确写“待确认”。

### 7. 初始化与迁移

- **7.1 初始化数据**：字典表、系统配置等基础数据随版本初始化；管理员账号首次启动创建（如适用）。
- **7.2 版本迁移**：每次结构变更提供可回滚迁移脚本，按版本号顺序执行。
- 原型未体现初始化数据与迁移策略时，标注“默认建议，待确认”。

### 8. 安全与权限

- **8.1 数据安全**：密码、手机号、邮箱、身份证、密钥、Token 等敏感字段加密存储、脱敏展示、操作留痕。
- **8.2 权限设计**：按角色分配数据访问权限，应用账号仅授予必需的表级读写权限；具体权限模型待确认。
- **8.3 容量与备份**：给出默认基线（并发量、数据保留、删除策略、加密、可用性），全部标注“待确认”；原型未提供数据量、峰值写入、分库分表需求时不要擅自设计分片。
- 不虚构等保、GDPR、个人信息保护法的具体合规结论。

### 附录

- **待确认事项**：字段类型、长度、必填、默认值、枚举值、关系、索引、数据量。
- **变更历史**：版本、日期、变更内容、变更人。
- **数据来源说明**：解析工具、原型目录、页面数、实体数、未纳入页面、模糊字段、便签纳入情况。

## 字段名映射建议

| 中文标签 | 建议字段名 |
|---------|-----------|
| 实例名称 | `instance_name` |
| 服务名称 | `service_name` |
| 服务类型 | `service_type` |
| 系统类型 | `system_type` |
| 配置名称 | `config_name` |
| 模板名称 | `template_name` |
| 版本号 | `version_no` |
| 状态 | `status` |
| 启用状态 | `enabled` |
| 创建时间 | `created_at` |
| 更新时间 | `updated_at` |
| 发布时间 | `published_at` |
| 触发时间 | `triggered_at` |
| 服务器 IP | `server_ip` |
| 所在 Vlan | `vlan` |
| URL | `url` |
| 备注 | `remark` |

无法可靠映射时使用 `field_<序号>`，并在说明中写“字段名待确认”，不要用拼音硬凑。

## 便签/备注说明的纳入

- 字段约束、枚举说明放入字段“说明”列。
- 业务规则影响索引或唯一性时，放入索引说明或待确认事项。
- 无法归属的备注放入附录“待确认事项”。
- 在“数据来源说明”标注：便签/矩形内备注说明已纳入字段说明、索引建议或待确认项。

## 生成脚本

```bash
# 1. 解析原型
python3 scripts/parse_axure.py <原型目录> --json > prototype.json

# 2. 生成数据库设计说明书
python3 scripts/generate_spec_docs.py prototype.json output/数据库设计说明书.md \
  --doc-type database-design --version v1.0.0
```

可选参数：

- `--project-name <名称>`：覆盖项目名。
- `--version <版本>`：写入封面版本号。

## 使用要点

1. **所有结论可追溯**：表名、字段名、类型、索引都要能对应到页面字段或明确标注“建议/待确认”。
2. **不生成空表**：没有业务字段的页面不建表，在附录说明。
3. **审计字段统一**：`id`、`created_at`、`updated_at` 每表必备。
4. **默认值与允许空要诚实**：未知就写“待确认”或 `-`，不要猜测。
5. **关系保守**：仅推断明确关系，其余放待确认。
6. **与详细说明书对齐**：实体名、字段中文名、功能编号保持一致。
