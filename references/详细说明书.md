# 详细说明书（md 格式）生成规范

本文件指导如何从原型解析数据生成详细说明书。当用户要求生成“详细说明书”“详细设计文档”“功能详细设计”时读取本文件。

## 输出文件

- 文件名：`详细说明书.md`
- 位置：原型目录下 `output/` 或用户指定位置
- 格式：Markdown（`.md`）
- 生成脚本：`scripts/generate_spec_docs.py --doc-type detailed-design`

## 文档定位

详细说明书回答“每个模块由哪些功能组成、用户怎么操作、系统怎么处理、异常怎么提示、字段怎么校验”。它以模块为一级章节，以功能项为最小描述单元，必须能直接支撑开发、联调和测试。

## 文档结构

```markdown
# [项目名称] 详细说明书

> 版本: v1.0.0 | 更新日期: YYYY-MM-DD | 文档类型: 详细说明书

## 1. 引言
### 1.1 编写目的
### 1.2 适用范围
### 1.3 术语与缩略语
### 1.4 参考资料

## 2. 总体说明
### 2.1 设计范围
### 2.2 模块划分
### 2.3 用户角色

## 3. 模块详细设计

#### 3.1.2 功能构成
#### 3.1.3 处理流程与交互
#### 3.1.4 业务规则与异常处理
### 3.2 [模块 B]
```

## 各章节生成规则

### 1. 引言

- **编写目的**：说明本文档用于各模块的功能构成、处理流程、交互规则与异常处理，作为开发实现、联调与测试验收依据。
- **适用范围**：列出纳入的页面；超过 12 页时列前 12 页并注明总页数。
- **术语与缩略语**：原型、页面、字段、P0-P2、待确认。
- **参考资料**：解析工具、原型根目录、页面数量。

### 2. 总体说明

- **设计范围**：给出页面数、模块数、功能项数。
- **模块划分表**：模块、功能项数、主要功能；主要功能列最多列 4 项，避免过长。
- **用户角色**：与《系统概要说明书》保持一致，不另造角色。

### 3. 模块详细设计

每个模块必须包含四小节：

#### 3.1.1 模块职责

一句话说明模块负责的业务处理与数据维护范围，并标注页面类型。不要写“该模块很重要”这类空话。

#### 3.1.2 功能构成

| 列 | 说明 |
|----|------|
| 编号 | `F-001` 全局递增，不按模块重置 |
| 功能 | 动作 + 对象，如“查看实例列表”“新增节点”“筛选查询模板列表” |
| 优先级 | P0/P1/P2 |
| 功能描述 | 一句话说明用户目标与系统行为 |

功能拆分建议：

- 页面主功能：查看/管理/配置/发布。
- 筛选查询：页面存在筛选区域时单独成项。
- 表单提交：页面存在 3 个及以上可输入字段时单独成项。
- 不要为装饰性按钮、纯文本、重复菜单生成功能项。

#### 3.1.3 处理流程与交互

每个功能项按编号展开：

```markdown
**F-001 查看实例列表**

- 进入页面，加载实例列表与筛选条件
- 选择筛选条件后点击查询，刷新列表
- 点击新增，打开新增表单
```

规则：

1. 优先使用原型中的交互事件（Click / Select / Load / Submit 等）。
2. 将事件翻译成“用户动作 → 系统响应”的业务语言，不直接粘贴 Axure 运行时代码。
3. 过滤以下噪声：`javascript:`、`localStorage`、`[[AxPlus...]]`、`$.ajax`、`eval(`、超长脚本、纯样式设置。
4. 纯 UI 状态（显示/隐藏、旋转、设置尺寸、选中状态、动态面板切换）可保留在详细说明书，但必须简短；不要整段复制。
5. 单条步骤建议不超过 160 字；无交互事件时写“原型未提取到交互事件，处理流程待补充”。
6. 表单功能要列出字段、必填/格式校验、提交成功与失败处理。

#### 3.1.4 业务规则与异常处理

- 原型有明确规则时逐条列出，并标注来源（便签/页面文本）。
- 原型未提供规则时写“原型未提供明确业务规则，校验与异常策略待确认”，不要编造。
- 至少考虑：必填校验、格式校验、重复提交、查询无结果、保存失败、权限不足、并发修改。
- 异常提示文案未知时写“提示文案待确认”，不要虚构具体文案。

### 4. 功能明细

- 在模块章节之后，按功能编号全局展开一次功能明细，避免模块章节信息过散。
- 每个功能包含：所属模块、优先级、所属页面、功能描述、字段说明（有字段时）、验收标准。
- 字段说明列：字段名 / 类型 / 必填 / 校验规则 / 默认值 / 说明；未知项标“待确认”。
- 验收标准用可勾选清单，至少覆盖页面打开、字段展示、主交互、异常提示。
- 与第 3 章模块章节内容保持一致；功能编号、优先级、字段名不得冲突。

### 5. 接口详细设计

- 按实体/页面给出建议接口，表列：接口名称、类型、提供方、调用方、说明。
- 说明列写建议方法与路径，如 `GET /api/instance/{id}`，并标注“建议，待确认”。
- 不展开鉴权、限流、幂等、重试的实现细节；如原型未体现，放入待确认。
- 同一实体的读取/保存/查询/发布接口尽量复用资源命名。
- 仅保留前 15 个核心接口；完整接口清单可在开发阶段补充。

### 6. 数据设计

- 给出实体清单：实体名、建议表名、来源页面、字段数、说明。
- 末尾注明“完整字段、索引与约束详见《数据库设计说明书》”，避免两份文档重复维护。
- 实体名、表名必须与《数据库设计说明书》一致。

### 7. 日志、异常与安全

- **7.1 日志设计**：关键业务操作、登录行为、异常错误；保留期限默认不少于 180 天（待确认）。
- **7.2 异常处理**：统一异常拦截、错误码、友好提示、不可恢复异常告警；文案与错误码待确认。
- **7.3 安全设计**：传输加密、登录态校验、接口鉴权、敏感数据脱敏、最小权限；均标注默认基线。
- 不虚构具体错误码、日志字段和加密算法。

### 附录

- **待确认事项**：字段类型、必填、默认值、校验规则、交互缺失、接口未定义。
- **需求追溯**：功能编号 ↔ 页面 ↔ 接口 ↔ 测试用例的建议映射。
- **变更历史**：版本、日期、变更内容、变更人。
- **数据来源说明**：解析工具、原型目录、页面数、功能数、便签纳入情况。

## 功能命名与优先级

| 场景 | 命名建议 | 默认优先级 |
|------|---------|-----------|
| 核心管理页 | 管理/查看 + 对象 | P0 |
| 配置页 | 配置 + 对象 | P0/P1 |
| 表单新增/编辑 | 新增/编辑 + 对象 | P0 |
| 列表查询 | 查看 + 对象 + 列表 | P1 |
| 筛选 | 筛选查询 + 对象 | P1 |
| 详情 | 查看 + 对象 + 详情 | P1 |
| 发布/版本 | 发布管理 / 版本管理 | P0/P1 |
| 登录/认证 | 登录 / 认证管理 | P0 |

优先级判断以“缺失后核心业务是否无法完成”为准，不按页面顺序。

## 便签/备注说明的纳入

- 业务规则、校验条件、状态流转放入“业务规则与异常处理”。
- 操作说明、字段解释放入对应功能步骤或字段说明。
- 无法归属的备注放入“待确认事项”。
- 在“数据来源说明”标注：便签/矩形内备注说明已纳入业务规则、交互步骤或待确认项。

## 生成脚本

```bash
# 1. 解析原型
python3 scripts/parse_axure.py <原型目录> --json > prototype.json

# 2. 生成详细说明书
python3 scripts/generate_spec_docs.py prototype.json output/详细说明书.md \
  --doc-type detailed-design --version v1.0.0
```

可选参数：

- `--project-name <名称>`：覆盖项目名。
- `--version <版本>`：写入封面版本号。

## 使用要点

1. **以功能项为最小单元**：每个功能都要有编号、描述、流程、规则。
2. **交互要翻译**：把原型事件翻译成业务步骤，不粘贴脚本。
3. **规则要诚实**：原型没有的校验、文案、异常策略一律标“待确认”。
4. **字段要可开发**：字段名、类型、必填、默认值、控件类型至少给出建议或待确认标记。
5. **与概要/数据库文档对齐**：模块名、功能编号、实体名保持一致。
