# 用户故事（md 格式）生成规范

本文件指导如何从原型解析数据生成结构化用户故事 Markdown 文件。当用户要求生成"用户故事"/"User Story"/"用户故事地图"时读取本文件。

## 输出文件

- 文件名：`用户故事.md`
- 位置：原型目录下 `_output/` 或用户指定位置
- 格式：Markdown（`.md`）

## 文档结构

```markdown
# [项目名称] - 用户故事

## 1. 文档信息
- 版本：v1.0
- 日期：YYYY-MM-DD
- 数据来源：原型解析

## 2. 角色定义
从原型中识别的用户角色清单

## 3. 用户故事地图
按角色 × 模块组织的用户故事总览表

## 4. 用户故事详表
按角色分组的完整用户故事

## 5. 验收标准汇总
所有故事的验收标准集中索引

## 6. 数据来源说明
```

## 角色定义

从原型中识别用户角色：

| 角色编号 | 角色名 | 说明 | 出现页面 | 备注 |
|---------|--------|------|---------|------|
| R1 | 运维人员 | 管理服务实例/配置发布/部署 | 实例管理/配置中心/发布 | 高权限 |
| R2 | 开发人员 | 服务注册/配置管理/版本管理 | 配置中心/版本管理/模板列表 | - |
| R3 | 系统管理员 | 认证管理/服务授权 | 认证管理/Authentication Manager | 全权限 |

**角色推断规则**：
1. 从页面名含"管理/Admin/Manager"推断对应角色
2. 从备注说明中提到的角色直接识别
3. 从控件的权限相关文字（"权限/授权/角色"）推断
4. 默认角色：若原型未明确，补"普通用户"角色并标注"（推测）"

## 用户故事格式

每个故事遵循标准模板：

```
### [故事编号] [故事标题]

**作为** [角色]
**我想要** [功能]
**以便于** [业务价值]

**验收标准：**
1. [可观测的条件 1]
2. [可观测的条件 2]
...

**优先级：** P0/P1/P2
**所属模块：** [页面名]
**备注：** [来自便签/矩形备注说明的补充信息]
```

**示例**：

```
### US-001 查看服务实例列表

**作为** 运维人员
**我想要** 查看所有服务实例的列表
**以便于** 掌握当前所有服务的运行状态

**验收标准：**
1. 进入实例管理页，列表默认加载所有实例
2. 列表含实例名称、版本、状态、服务器 IP 字段
3. 状态以颜色标签区分（running/ stopped/error）
4. 列表支持按节点类型筛选

**优先级：** P0
**所属模块：** 实例管理
**备注：** 树形导航筛选可见（来自备注说明）
```

## 用户故事地图

总览表按角色 × 模块组织：

| 模块 \ 角色 | R1 运维 | R2 开发 | R3 管理员 |
|------------|---------|---------|---------|
| 实例管理 | US-001, US-002 | - | - |
| 配置中心 | US-005 | US-006, US-007 | - |
| 认证管理 | - | - | US-010, US-011 |

## 故事推断规则

1. **页面 × 角色 = 故事候选**：每个页面对应至少 1 个故事，按角色拆分
2. **控件映射故事**：

| 控件类型 | 推断故事 |
|---------|---------|
| 表格 | 查看 XX 列表 |
| 输入框 + 按钮 | 新增/编辑 XX |
| 树形导航 | 按节点筛选 XX |
| 查询按钮 | 按条件搜索 XX |
| 发布/确定按钮 | 提交/发布 XX |
| 详情链接 | 查看 XX 详情 |

3. **验收标准来自页面内容**：原型中的文本字段、状态标签、约束都转为验收标准
4. **业务价值从备注推断**：备注说明的业务规则帮助明确故事价值

## 便签/备注说明的纳入

原型解析数据中每页的 `notes` 字段（便签/矩形内备注说明）应：

- **补为独立故事**：备注说明的是一项可操作的业务规则时，生成对应故事
  - 例：备注"Access Token 有效期 24 小时" → 故事"管理 Token 有效期"
- **补入验收标准**：约束类说明转为故事的验收标准
  - 例：备注"跨 VLAN 调用验证不通过" → 验收标准"跨 VLAN 的服务调用应被拒绝"
- **补入故事备注列**：业务规则说明填入故事的"备注"字段
- **影响角色识别**：备注中提到的角色直接识别为角色定义
- **明确业务价值**：备注说明的业务目的帮助明确"以便于"部分

在文档末尾的"数据来源说明"标注：便签/矩形内备注说明已纳入故事、验收标准与角色定义。

## 生成脚本

**对应脚本**：`scripts/generate_user_stories.py`（可独立执行）。

**用法**：
```bash
# 先用 parse_axure.py 拿到解析 JSON
python3 scripts/parse_axure.py <原型目录> --json > prototype.json

# 再跑生成脚本
python3 scripts/generate_user_stories.py prototype.json [输出路径]
```

脚本会按本文件的列定义/分组/便签纳入规则生成 `用户故事.md`。若需调整推断逻辑，直接编辑该脚本对应函数。

## 使用要点

1. **角色保守推断**：无法确定时标"（推测）"，不要编造角色名
2. **每页至少 1 个故事**：页面无明确功能时，故事写"查看该页面内容"
3. **验收标准可观测**：每条标准必须是可测试的具体条件，避免"正常工作"等模糊表述
4. **故事编号全局递增**：`US-XXX` 不按角色/模块重置
5. **备注说明优先**：`notes` 字段补为独立故事、验收标准或故事备注
6. **业务价值诚实**：无法明确价值时写"完成 XX 操作"，不要夸大业务影响
7. **故事地图可选**：页面少于 5 个时可省略地图，直接展示详表
8. **不编造未体现的角色**：原型只有运维相关功能时，不要补"产品经理/运营"等角色
